# Code Review（两轴）

本技能是 `.zcode/skills/code-review/SKILL.md` 的**薄封装**；流程细节与坏味道清单以源文件为准，本文件只补 DO 项目的落地差异。

## 为什么是两轴、且不合并

代码可以通过一轴、挂掉另一轴：**照足标准但做错东西**（Standards 过 / Spec 挂），或**完全按要求做但破坏约定**（Spec 过 / Standards 挂）。合并排序会让一轴掩盖另一轴，所以**两轴分开报告**，最后只各给一句总结，不评选"总冠军"。

## 1. 定固定点

用户给的那个（commit / branch / tag / merge-base）就是固定点。**本项目常见情况是改动还没提交**——此时：

- 固定点 = 当前 `HEAD`
- 被评审对象 = **工作区**：`git diff HEAD`（含删除）**加上未跟踪的新文件**（它们不在 diff 里，必须单独读）
- 把 diff 导出成一个文件再交给子代理读（子代理跑不了 git），并在提示里列出未跟踪文件清单

## 2. 定 Spec 来源

本项目 issue tracker 是 local 型（`sdlc.config.yaml` 的 `issue_tracker.type: local`，不走远端）。Spec 按此顺序取：

1. `.sdlc/changes/<change-id>/plan.md` 与 `design.md`
2. `docs/TODO.md` 里对应任务条目（含用户原话与判定）
3. `docs/design/DESIGN.md` 的 §5 与 §9 决策记录

⚠️ **本项目特有的坑**：这些记录常常是**改动作者自己写的**，会把没落地的东西写成已完成。所以 Spec 轴的第一要务是把记录当成**待验证的声明**，逐条到代码里核对 —— 特别是动效参数表、"硬约束"是否真被遵守、以及"未启用/已删除"的实现是否还在被引用。

## 3. 定 Standards 来源

- `AGENTS.md`（工作区约定）
- `docs/design/DESIGN.md` §5（动效契约：§5.0 原则、§5.1 硬约束、§5.2 参数、§5.3 清单）——**违反明文契约算硬违规**
- 源文件里的坏味道基线（Fowler ch.3）：仓库明文标准**优先于**基线；基线一律只是 judgement call
- **跳过工具能管的东西**（类型、格式、lint）

## 4. 并行跑两轴，然后自己复核

按源文件要求起两个并行子代理。**聚合前必须自己复核**：子代理会误报（例如只看局部就断言"覆盖不全"、把 `initial` 的缺失说成整段缺失）。逐条到代码里验证，**在报告里明确列出剔除的误报**——这比多报几条更有价值。

## 5. 收尾

- 报出确认的问题，区分**硬违规 / judgement**；
- 真问题当场修（能修的小问题不要留给下一轮）；
- 未动的 judgement 项要列出来并说明为什么没动；
- 评审结论落进 `.sdlc/changes/<change-id>/test.md`（这是六阶段的一部分，不是额外产物）。
